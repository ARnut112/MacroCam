# ฐานข้อมูล MacroCam

ไฟล์ในโฟลเดอร์นี้เตรียมไว้สำหรับ **Supabase โปรเจกต์ใหม่ของ MacroCam เท่านั้น** ไม่ใช้ฐานข้อมูล คีย์ หรือ bucket ของ Bakkabook เดิม

## ลำดับเปิดใช้งาน

1. สร้าง Supabase โปรเจกต์ใหม่ แล้วเปิด SQL Editor
2. รัน `migrations/202610150001_macrocam.sql` เพียงครั้งเดียว ระบบจะสร้างตาราง ฟังก์ชัน สิทธิ์ และ bucket ให้ครบ
3. ใน Authentication → Users สร้างผู้ดูแลด้วยอีเมลจริงของเจ้าของร้าน และตั้งรหัสผ่านที่ปลอดภัย จากนั้นเพิ่ม UUID ของผู้ดูแลลง `public.admin_users` ตามตัวอย่างด้านล่าง
4. นำ URL, anon key และ service role key ของ **โปรเจกต์ MacroCam** ไปใส่ตัวแปรฝั่งเซิร์ฟเวอร์ตาม `.env.example` ห้ามใส่ service role key ในตัวแปรที่ขึ้นต้นด้วย `NEXT_PUBLIC_`
5. เข้าหลังร้าน เพิ่มสินค้า ตรวจจำนวนคงเหลือ อัปโหลด QR และระบุบัญชีรับเงินจริงที่นัทยืนยัน
6. ใส่นโยบายจัดส่ง คืนสินค้า ประกัน และข้อมูลส่วนบุคคลที่นัทยืนยันครบทั้ง 4 ส่วน ไม่ใช้ข้อความตัวอย่างเป็นนโยบายจริง
7. ทดสอบโปรเจกต์ทดสอบให้ครบก่อนตั้ง `STORE_CHECKOUT_ENABLED=true` ในสภาพแวดล้อมที่ต้องการเปิดรับคำสั่งซื้อ

ตั้ง `ORDER_ACCESS_SECRET` เป็นค่าสุ่มลับความยาวอย่างน้อย 32 ตัวอักษรและเก็บไว้ฝั่งเซิร์ฟเวอร์ หากไม่มีค่านี้ระบบคำสั่งซื้อจะปิดรับการทำงาน เช่นเดียวกับกรณียังไม่มีคีย์ Supabase ครบ การรับคำสั่งซื้อจริงต้องตั้ง `STORE_CHECKOUT_ENABLED=true` โดยตรง ค่าอื่นหรือไม่ตั้งค่าจะไม่รับคำสั่งซื้อ

```sql
-- แทน UUID ด้วยค่า id ของบัญชีผู้ดูแลใน Authentication → Users
insert into public.admin_users (user_id)
values ('00000000-0000-0000-0000-000000000000')
on conflict (user_id) do nothing;
```

ตัวอย่าง UUID ข้างต้นใช้ไม่ได้จนกว่าจะเปลี่ยนเป็นผู้ใช้จริงที่มีอยู่แล้ว ระบบไม่เปิดสิทธิ์ผู้ดูแลตามอีเมลจากหน้าเว็บ และไม่เปิดให้ผู้ใช้ทั่วไปเพิ่มสิทธิ์ตัวเอง

## การหมดอายุ 1 ชั่วโมง

นัทยืนยันระยะเวลา **1 ชั่วโมง** สำหรับคำสั่งซื้อที่ยังไม่ส่งสลิป ระบบจองสต็อกเมื่อสร้างคำสั่งซื้อ และตั้ง `expires_at` เป็นเวลาสร้างบวก 60 นาที

- เมื่อสร้างคำสั่งซื้อ ติดตามคำสั่งซื้อ หรืออ่านรายการหลังร้าน เซิร์ฟเวอร์จะจัดการรายการที่เกินเวลาและคืนสต็อก
- หน้าชำระเงินไม่สามารถแนบสลิปเมื่อพ้นกำหนด แม้ยังไม่มีคำขออื่นเข้ามาจัดการการหมดอายุ
- รายการที่ส่งสลิปทันเวลาจะรอร้านตรวจเอง และไม่หมดอายุด้วยกฎนี้
- ฟังก์ชัน `expire_orders()` และการยกเลิกล็อกแถวก่อนคืนสต็อก จึงกดซ้ำได้โดยไม่คืนซ้ำ
- การตรวจหมดอายุใช้เวลาจริงหลังได้ล็อกคำสั่งซื้อ ไม่ยึดเวลาเริ่มคำขอ กรณีรอล็อกจนเลยกำหนดจึงไม่รับสลิปย้อนหลัง
- หากต้องการคืนสต็อกแม้ไม่มีคนเปิดเว็บ ต้องเพิ่มงานตั้งเวลาเรียก `/api/cron/expire-orders` ด้วย `Authorization: Bearer <CRON_SECRET>` หรือเรียก SQL `select public.expire_orders();` จากตัวตั้งเวลาที่เชื่อถือได้
- ควรตั้งให้ทำงานทุก 1 นาที งานหนึ่งครั้งประมวลผลสูงสุด 500 รายการ การคืนสต็อกจึงเกิดหลังพ้นกำหนดเมื่อรอบทำงานถัดไปมาถึง

Migration **ไม่ได้ติดตั้งหรือเปิดงานตั้งเวลาอัตโนมัติ** ระหว่างพัฒนา ช่อง `runtime_config.scheduled_expiry_enabled` เป็นตัวบันทึกว่าตั้งงานไว้แล้วเท่านั้น ไม่ได้สร้างตัวตั้งเวลาให้ หากเปิดจริงให้ตั้งค่านี้เป็น `true` หลังตรวจว่างานเรียกสำเร็จ และลบ/ปิดงานตั้งเวลาเมื่อหยุดใช้งาน

```sql
update public.runtime_config set scheduled_expiry_enabled = true where singleton = true;
```

## ขอบเขตสิทธิ์

- ตารางแอปทั้งหมดเปิดและบังคับ RLS โดยไม่มี policy ให้ `anon` หรือ `authenticated` อ่านข้อมูลโดยตรง หน้าร้านอ่านเฉพาะข้อมูลปลอดภัยผ่าน API ของเซิร์ฟเวอร์
- `service_role` อ่านคำสั่งซื้อได้ แต่เปลี่ยนสถานะหรือสร้างคำสั่งซื้อผ่าน RPC เท่านั้น ไม่ให้สิทธิ์แก้ตารางคำสั่งซื้อโดยตรง
- รูปสินค้า QR และสลิปรองรับ JPG, PNG และ WEBP ขนาดไม่เกิน 4 MiB (4,194,304 ไบต์; หน้าเว็บเรียก 4 MB) ต่อไฟล์ เพื่อเผื่อข้อมูลฟอร์มให้อยู่ใต้[เพดานคำขอ 4.5 MB ของ Vercel](https://vercel.com/docs/functions/limitations)
- `slips` เป็น bucket ส่วนตัว ไม่มี policy ให้ลูกค้าอ่านหรือเขียนโดยตรง เซิร์ฟเวอร์ตรวจขนาด ชนิด MIME และลายเซ็นไฟล์จริงก่อนอัปโหลด และให้ลิงก์ชั่วคราวแก่ผู้ดูแลที่ผ่านการตรวจสิทธิ์
- `store-assets` เป็น bucket สาธารณะสำหรับรูปสินค้าและ QR เท่านั้น ห้ามเก็บสลิปหรือข้อมูลลูกค้าใน bucket นี้
- `admin_users` เป็น allowlist อ้างอิง `auth.users` เซิร์ฟเวอร์ต้องตรวจผู้ใช้ผ่าน Supabase Auth ก่อนส่ง `p_actor_id` ให้ RPC
- สินค้าที่เคยมีรายการสั่งซื้อถูกป้องกันการลบด้วย foreign key ข้อมูลใน `order_items` เก็บชื่อ ราคา และรูป ณ เวลาสั่งซื้อ
- API แก้สินค้าให้ส่ง `updatedAt` ที่อ่านมาพร้อมสินค้า และอัปเดตเฉพาะแถวที่ `updated_at` ยังตรงกัน หากมีการจองสต็อกหรือผู้ดูแลอีกคนแก้ข้อมูลไปก่อน จะตอบ 409 และให้โหลดข้อมูลใหม่ ป้องกันการบันทึกสต็อกเก่าทับยอดที่เพิ่งถูกจอง การซ่อนสินค้าก็ใช้การตรวจรุ่นข้อมูลเดียวกัน
- การสร้างคำสั่งซื้อยึดล็อกอ่านร่วมของการตั้งค่ารับเงินและนโยบายจน transaction เสร็จ ป้องกันการล้างข้อมูลตั้งค่าระหว่างตรวจและบันทึกคำสั่งซื้อ
- ห้ามเปิดเผยค่าภายในจาก RPC ทั้งแถวให้ลูกค้าโดยตรง โดยเฉพาะ `customer_fingerprint`, `request_hash` และ `slip_path` API ต้องแปลงข้อมูลก่อนตอบกลับ

## สัญญาของ RPC

ทุก RPC ด้านล่างอนุญาตเฉพาะ `service_role` เท่านั้น ฟังก์ชันภายในอยู่ใน `macrocam_private` และไม่เปิดให้ client เรียก

| RPC                                                                                                                                            | ผลลัพธ์                           | หน้าที่                                                                                   |
| ---------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- | ----------------------------------------------------------------------------------------- |
| `create_order(p_payload jsonb, p_idempotency_key uuid, p_customer_fingerprint text)`                                                           | `jsonb` ของ orders                | ตรวจข้อมูล/การตั้งค่า/ราคา/สต็อก ล็อกสินค้า เก็บ snapshot และจองสต็อกใน transaction เดียว |
| `attach_slip(p_order_id uuid, p_slip_path text)`                                                                                               | `jsonb` ของ orders                | ตรวจเวลาและไฟล์ใน private bucket เก็บไฟล์แรกที่ยอมรับ เปลี่ยนเป็นรอตรวจสลิป               |
| `transition_order(p_order_id uuid, p_status text, p_actor_id uuid, p_shipping_company text default null, p_tracking_number text default null)` | `jsonb` ของ orders                | ตรวจ allowlist และลำดับสถานะผู้ดูแล                                                       |
| `complete_order(p_order_id uuid)`                                                                                                              | `jsonb` ของ orders                | ลูกค้ายืนยันรับแล้วได้เฉพาะสถานะส่งแล้ว; การกดซ้ำคืนรายการเดิม                            |
| `expire_orders()`                                                                                                                              | จำนวนรายการที่หมดอายุ (`integer`) | หมดอายุเฉพาะรายการที่ยังไม่ส่งสลิป และคืนสต็อกครั้งเดียว                                  |
| `consume_rate_limit(p_key text, p_limit integer default 10, p_window_seconds integer default 900)`                                             | `boolean`                         | ตัวนับแบบ atomic; `false` เมื่อเกินจำนวนในหน้าต่างเวลา                                    |

Payload สั่งซื้อมี `recipient_name`, `phone`, `address`, `note` และ `items` แต่ละรายการมี `product_id` กับ `quantity` เท่านั้น ราคาใช้จากฐานข้อมูลเสมอ การส่งราคาอื่นใน payload ไม่มีผล

การเรียกซ้ำด้วย idempotency key เดิมคืนคำสั่งซื้อเดิมได้เฉพาะ fingerprint และข้อมูลคำสั่งซื้อที่ตรงกัน ข้อมูลรายการถูกจัดลำดับและรวมสินค้าซ้ำก่อนทำ hash การใช้ key เดิมกับคนอื่นหรือข้อมูลใหม่ถูกปฏิเสธด้วย `IDEMPOTENCY_CONFLICT`

ลำดับสถานะ: `awaiting_payment → slip_submitted → paid → shipped → completed` ผู้ดูแลยกเลิกได้เฉพาะ `awaiting_payment`, `slip_submitted`, `paid` ห้ามยกเลิกรายการที่ส่งแล้ว การส่งต้องระบุทั้งบริษัทขนส่งและเลขติดตาม

การแนบสลิปยัง **ไม่ถือว่าชำระสำเร็จ** ไม่มี AI ตรวจสลิป และไม่มีการเชื่อมต่อ LINE

## การทดสอบ

`tests/invariants.sql` เป็นชุดตรวจฐานข้อมูล ใช้เฉพาะฐานข้อมูลทดสอบว่างหลังรัน migration เท่านั้น ชุดทดสอบสร้างผู้ดูแลและสินค้าจำลองภายใน transaction แล้ว `rollback` ทั้งหมด ตรวจสิทธิ์ การตั้งค่ารับเงิน ราคา สต็อก การกดซ้ำ idempotency การแนบสลิป การยืนยัน/จัดส่ง/รับสินค้า การยกเลิก การหมดอายุ และ rate limit

**สถานะส่งมอบ:** รัน migration และชุดทดสอบ SQL ผ่านแล้วใน PostgreSQL แบบฝังตัว (PGlite 0.5.10) ที่แยกจากร้านจริง โดยสร้าง schema จำลองขั้นต่ำสำหรับ `auth` และ `storage` ตรวจสิทธิ์ `service_role` สำหรับสินค้า การตั้งค่า และการเรียกสร้างคำสั่งซื้อแล้ว ข้อมูลทดสอบ rollback ทั้งหมด ไม่มีคำสั่งซื้อเหลือหลังทดสอบ ยังไม่ได้รันกับ Supabase จริง และยังไม่ได้ทดสอบ Supabase Auth, Storage HTTP API หรือล็อกข้ามหลาย session ค่ะ

ตัวเรียกทดสอบซ้ำอยู่ที่ `tests/local-postgres.cjs` ต้องติดตั้ง `@electric-sql/pglite` แยกในโฟลเดอร์ชั่วคราวแล้วส่งตำแหน่งโมดูลเป็นอาร์กิวเมนต์แรก ไม่ต้องเพิ่มเป็น dependency ของเว็บ ตัวทดสอบใช้ฐานข้อมูลในหน่วยความจำและไม่ใช้คีย์จริง

ก่อนเปิดขายให้ทดสอบเพิ่มด้วย 2 session ที่สั่งสินค้าชิ้นสุดท้ายพร้อมกัน ต้องมีคำสั่งซื้อสำเร็จเพียงรายการเดียว อีกคำขอได้ `STOCK_UNAVAILABLE` จากนั้นทดสอบกด key เดิมพร้อมกัน ต้องได้ UUID คำสั่งซื้อเดียวและสต็อกลดครั้งเดียว ตรวจอีกครั้งว่าผู้ใช้ anon/authenticated เรียก RPC ไม่ได้ และ URL สาธารณะของ bucket `slips` เปิดไม่ได้

ทดสอบหลังร้านเพิ่มอีกกรณี: เปิดหน้าแก้สินค้าที่มีสต็อก 1 ชิ้นค้างไว้ แล้วสั่งสินค้านั้นผ่านอีกหน้าต่างจนจองสำเร็จ กลับมาบันทึกหน้าแก้เดิมต้องได้ 409 โดยสต็อกยังเป็น 0 ไม่กลับเป็น 1 เมื่อรีเฟรชหลังร้านจึงแก้ข้อมูลรุ่นล่าสุดได้

ไม่มีไฟล์ใดในโฟลเดอร์นี้นำข้อมูลขึ้นฐานข้อมูลจริงหรือเผยแพร่เว็บไซต์โดยอัตโนมัติ
